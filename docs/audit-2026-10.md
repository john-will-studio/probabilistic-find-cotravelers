# Independent audit and generality study (October 2026)

Question: will this work on all types of datasets, for finding unknown objects that travel with a known one in a large haystack? Short answer for the repo as imported: no. For the current code: it works across a much wider range (sparse and dense cadence, any extent, dirty input, Python 3.12 and 3.14), with stated limits below.

## Method

- Own study: bundled benchmark and domain smoke tests re-run on Python 3.14 / pandas 3; ArcGIS "Find co-travelers" Camp Lemonnier geodatabase (1.29M phone pings, 1.06M vehicle points, Esri's own 100 ft / 10 s co-traveler layer as a weak reference, not ground truth); NOAA AIS 2023-01-01 (8.1M rows, US waters) with planted companions as known truth.
- Independent reviewers, each on a private copy with its own harness: Codex (`gpt-6-astra`) and a Sonnet 5.5 subagent, two rounds (original code, then the improved code).
- Fixes were verified against the reviewers' own repro cases, not only mine.

## Round 1 findings (original code)

1. Python 3.14 / pandas 3: elapsed time computed assuming nanosecond timestamps, so seconds were 1000x too small; recall 0 with exit code 0.
2. One bad coordinate, or any data spanning more than 1 degree, aborted the whole run (the real phone data has 27,520 rows from 7 phones outside the main area; AIS and aircraft data always span more).
3. A 15-minute window needing 3 fixes and no 10-minute gap discarded sparse or bursty data (84% of real phone windows "unknown"; zero co-travel events).
4. Acceptance needed 2 UTC days, so one-off single-day companions were never accepted.
5. Crowd discount 1/(1+crowd) made true companions in crowds mathematically unable to pass; co-dwell dominated accepted pairs.
6. Overtaking was scored as sustained co-travel; offset companions and followers (time lag) unreachable.
7. Input: naive timestamps, `+0000`, literal `NA`/`NULL` IDs, equivalent-time duplicates, silent empty results for bad focal IDs, stale outputs after failed reruns.
8. Scale: candidate search ignored the focal list and used the largest uncertainty in the window.

## What changed

See README and `skills/score-mover-associations/references/method.md`. In short: unit-independent time; region partition and overlapping tiles (antimeridian aware); sparse point-pair evidence; adaptive window, lag and radius scenarios; overtaking checked at both ends of the shared interval with velocity-fit uncertainty; focal-first bounded searches; input hardening; `adapt.py`; `sweep.py` with a null.

## Known limits (do not oversell)

- The family-wise test is conservative at 20 replicates on a single day of data; strong but not top-ranked companions can be left unflagged. More replicates and the ranked `sweep_pairs.csv` are the remedy. The day-permutation null needs at least 4 UTC days; shorter data use a time-shift null that does not preserve bursty observation windows.
- Calibration was validated on synthetic nulls only. Real data keeps individual habits; two movers with the same schedule and venue are indistinguishable from companions at wide radii. Check `best_radius_m` against the data's error.
- The Esri layer is another method's output. Agreement with it is indicative, not precision/recall. Phone accuracy (50 m at 95%) and AIS accuracy (15 m at 95%) are declared assumptions.
- Not implemented: elliptical or 3D errors, polar data, calibrated interaction probabilities, a fixed-time-of-day-aware null for single-day data, event day-splitting at midnight (days are counted by start date), exported start/end coordinates for window events are window centres.
- Slow motion (below about 1.3 m/s) is classified co-dwell; continuous multi-day shared stays count as one day.

## Round 2 (independent re-audit of the improved code)

Codex and Sonnet each re-ran their own round-1 harnesses plus new adversarial cases. Both confirmed the pandas 3, dirty-coordinate, wide-extent, antimeridian, follower (with `--lag-seconds`), irregular-cadence and adapter fixes. Defects they found were fixed in this repo: sparse-path memory (11 GB at 1M rows), significance calibration (symmetric reference pools, family-wise p, schedule-preserving null), tile duplicate events, date-only timestamps, adapter chunk/offset/nanosecond handling and atomic publishing, stale sweep outputs, slow overtakes. Sonnet additionally confirmed the sweep finds 5/5 planted companions with 0 false positives on 1-day and 3-day synthetic data, and that `adapt.py` handles epoch seconds, alternate separators, literal `NA` IDs and ID filters.

Reported and not fully resolved:

- Commuter-style data: the conservative `significant` column found 0 of 4 planted pairs while `significant_any_model` found 4 of 4 with no false positives (Sonnet, one fixture). Report both columns and say which supports a finding.
- The fixed `accepted` rule still lets co-dwelling colleagues through (15 accepted, none true in Sonnet's commuter generator). `dwell_only` now flags pairs whose evidence is entirely co-dwell, and one-day data no longer requires two days, but a clean single 30-minute episode still scores below 70; use `sweep.py` significance for single-day or short records.
- Cost: `sweep.py` took about 13 minutes at 450k rows (10 replicates, 4 workers) and was not run on the 1.29M-row phone file by that reviewer (it ran in about 4 minutes for a focal run on my machine with the window cache). A 6.5M-row single-scenario run used 12.8 GB resident.
- Loosely coupled convoys beyond the default 100 m radius need a larger radius (the sweep grid includes 250 m).
- Same-time conflicting fixes are still quarantined rather than averaged.
- Commuter null coverage was incomplete (1 of 5 planned finished), so habit-sharing false positives are only partly tested.

## Memory, Windows and a 32 GB machine

An earlier overnight run forced a restart of the development Mac. Cause: the sparse matcher built a Python list of crowd neighbours for every candidate pair at once (estimated 4 GB at the default tolerance, 39 GB at 360 s and 430 GB at 1200 s on a 300k-row fixture), multiplied by 12 to 16 forked sweep workers, with several other heavy jobs running at the same time.

Fixes: time-sliced matching with a capped pair count and batched crowd counts (same results as the unsliced version, tested); a sweep memory budget (40% of RAM, at most 24 GB, at most 70% of free memory) that sizes the worker count; slimmed per-worker data; worker recycling; a watchdog that stops the sweep cleanly at 1.25x the budget (verified: exit code 3, reason recorded, shell untouched); reading only the needed CSV columns; streaming file hashes; `spawn` start method for Windows (verified here with `COTRAVELER_START_METHOD=spawn`: identical results to fork); `psutil` for cross-platform RAM and process memory.

Measured (macOS, Python 3.14, pandas 3, `spawn`, 12 GB budget, the commuter fixture of 302k rows, default 18-scenario grid x 21 datasets): 381 s wall, 10 workers, peak 9.4 GB total across all processes. An earlier run with 4 workers peaked at 3.6 GB. Largest single scenario (250 m, 1200 s tolerance) went from an estimated hundreds of GB to 0.9 GB; 1M rows focal 0.8 GB; 10M rows focal 7.1 GB. On a 32 GB Windows machine the default budget is about 12.8 GB. Not run on Windows itself: the Windows path is emulated by `spawn` and by avoiding POSIX-only calls on the default path.

Other speedups verified identical to the previous exact code: vectorised window fits (100x), vectorised pairing (5-10x), sparse search with time scaled to the search reach (3-20x; candidate sets identical), crowd window fixed at half a motion window regardless of the matching tolerance.

Note on timing: long background jobs on the laptop occasionally stalled by orders of magnitude (the same 3 s scenario once took 905 s) until they were run under `caffeinate`; this was the machine throttling background work, not the code.
